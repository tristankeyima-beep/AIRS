### 2.1 ADP 预览器中的页内跳转失效

现象：

- ADP 内点击左侧报告目录没有滚动。
- ADP 内点击检查能力卡片的“查看”没有滚动。
- Chrome 直接打开同一 HTML 时，目录和“查看”均可正常跳转。

## 3. 实际报告的总体判断

本例原审核结论为“不通过”。根据当前材料、规则 1001、规则 1002 及顶层 AND 逻辑，维持“不通过”目前有规则和材料支持。

问题主要不在最终资格结论，而在以下方面：

- 把兼容性警告误写成规则质量缺陷。
- 同一个证据编号错位根因被重复记成两个问题。

## 4. P0：优先修复项

### P0-1 纠正“标准可执行”与报告建议之间的矛盾

实际证据：

- `inspect_standard.py --profile qc` 对本例标准返回：
  - `kind=structured_complete`
  - `structural=true`
  - `executable=true`
  - `traceable=true`
- 当前警告仅包括：
  - 非模式 1 正式契约结构。
  - 提取项缺少 `keywordCode`。
- 使用现有 `evaluate_logic.py`，输入规则 1001、1002 均为“不满足”，可以确定性得到顶层 AND 结果“不满足”。

当前错误表现：

- 报告把“标准格式非契约结构”记为一条规则维护质量问题。
- 总体建议要求“补充完整结构化标准以启用脚本化逻辑树校验”。
- 规则维护建议要求补充 `keywordCode` 才能进行逻辑树校验。

这些表述与实际能力矛盾：四位规则编码和缺少 `keywordCode` 不妨碍基于 `ruleCode` 运行顶层逻辑树。

期望行为：

- QC profile 的兼容性 warning 不自动升级为业务问题。
- 标准已经 `structured_complete + executable=true` 时，不得再建议“补充完整结构化标准”。
- 标准可执行且条件一致性检查为已完成时，必须运行逻辑树计算并保存追踪结果。
- 只有真正阻断执行的缺陷才能把标准标记为 `structured_incomplete`。

建议涉及：

- `SKILL.md`
- `references/input-adapters.md`
- `references/qc-rubric.md`
- `references/report-contract.md`
- `scripts/prepare_qc_report.py`
- `scripts/render_qc_html.py`
- 集成测试与真实案例回归测试

验收标准：

- 本例不再产生“标准格式非契约结构”问题。
- 本例不再建议补充 `keywordCode` 才能运行逻辑树。
- 报告中能看到顶层 AND 的确定性计算结果及其摘要。
- 文本版与 HTML 版的逻辑追踪结果一致。

### P0-2 强制一处根因只生成一条问题

实际证据：

- 原审核引用了不存在于已确认材料清单中的材料 ID，尾号为 `4085`。
- 被引用的原文实际存在于材料 ID 尾号为 `4083` 的“住院病历-5”中。
- 当前报告将其拆为：
  1. “引用了未提供的材料”。
  2. “证据溯源 ID 错位”。

根因判断：

这不是两件独立事件，也不能直接等同于“患者漏传材料”。它是同一条原审核证据的材料编号标注错误。

期望行为：

- 只生成一条根因问题。
- 主类别建议使用“证据提取准确性”。
- 通过 `relatedCapabilities` 关联“材料缺失判断准确性”。
- inventory 仍可记录 `referencedButMissing`，但不得因此再生成第二条问题。
- 业务表述使用“原审核引用的材料编号无法在清单中找到；同一原文位于另一已提供材料”，避免使用“患者缺少材料”或“材料幻觉”。

需要进一步设计的脚本约束：

- 是否将 `issueId` 从可选改为必填。
- 是否增加可稳定去重的 `rootCauseKey`。
- 如何识别“同一错误材料 ID + 同一引用原文”产生的跨能力重复问题。
- 如何避免过度依赖文本相似度造成误合并。

验收标准：

- 本例该根因只计数一次。
- 两个能力区块均可链接到同一问题。
- “问题数量”与唯一根因数一致。
- “材料缺失复核”不得暗示用户漏传已确认不存在的材料。

### P0-3 收紧“隔离盲审”的命名与可信证明

当前风险：

- ADP 在同一次上下文中完成复核并读取原审核结果时，不能仅凭报告对象证明真正隔离。
- 模型在同一次上下文中读过原审核结果后，仍可能把 `mode` 写成 `isolated_blind`。
- 给模型增加 `generatedInIsolatedContext=true` 仍是自我声明，不构成证据。
- 用盲审结果与原审核结果的文本重叠率判断是否真盲，会误伤正常的一致结论，也无法证明隔离。

期望行为：

- 默认使用 `independent_non_blind`。
- 只有执行平台确实创建独立上下文，并能提供可信的执行证明时，才允许使用 `isolated_blind`。
- 非盲复核必须在业务报告中清楚披露确认偏差限制。
- 可信证明应来自编排层或工具执行层，而不是模型自行填写。

后续设计候选：

- 增加由可信执行器提供的隔离运行 ID、上下文 ID、开始时间和产物摘要。
- 明确哪些字段是模型可写，哪些字段只能由执行器写。
- 如果 ADP 无法提供可信证明，则该平台生成的报告一律不得自称盲审。

验收标准：

- 如果独立复核与原审核结果的读取发生在同一次上下文中，报告必须标注为“独立二次复核（非盲）”，不得称为“隔离盲审”。
- 缺少可信证明时，`isolated_blind` 必须被拒绝或降级。
- 不采用模型自填布尔值作为隔离证明。

### P0-3A 重新评估 SHA-256 是否应作为模式 2 的强制契约

待决策问题：

SHA-256 不能让原审核结果对复核模型不可见，也不能证明复核真的发生在独立上下文中。它只能检查原始输入、确认清单或冻结复核产物后来是否发生变化。如果执行平台本身能够：

- 在真正独立的上下文中完成复核；
- 在复核完成前不向该上下文提供原审核结果；
- 保存不可变的复核运行产物；
- 提供可信的运行 ID、上下文 ID、输入版本和产物版本；

那么 `artifactSha256` 对“降低确认偏差”的价值可以由平台的隔离和不可变运行记录替代，继续把它作为模型可见的强制字段只会增加 Skill 契约、报错和报告复杂度。

建议方向：

- 首要保障应是“原审核结果不可见的独立复核环境”，而不是 SHA-256。
- 先确认目标运行环境是否真的支持独立上下文和不可变产物，再决定是否删除摘要字段。
- 如果平台提供可信的独立运行 ID 和不可变产物，可移除 `artifactSha256` 的强制门槛，改为记录 `reviewRunId`、输入版本和完成时间。
- `rawInputSha256`、`inventorySha256` 若仍用于确认用户确认的是哪一版输入，可以保留为脚本自动生成的内部技术元数据，但不要求模型填写，也不在业务报告主页面展示。
- 如果平台不提供输入版本或不可变产物，摘要仍有审计价值，但必须明确：它只能发现变化，不能证明隔离、不能阻止修改、不能证明判断正确。
- 不建议一次性删除全部摘要字段；应按“隔离证明、输入版本绑定、产物不可变性”三种用途分别评估替代机制。

验收前置条件：

- 明确 ADP 是否支持真正独立的模型调用或独立上下文。
- 明确独立调用是否能在完成前完全看不到原审核结果。
- 明确平台是否提供可信且不可由模型伪造的运行 ID 和产物存储。
- 在上述能力未确认前，本项保持“待决策”，不直接删除现有 SHA-256 契约。

### P0-4 冻结产物的材料原文必须可逐字追溯

实际证据：

- 本例冻结产物包含 6 条 `materialFacts[].rawText`。
- 6 条均不能在对应 `materialContent` 中逐字找到。
- 部分 `rawText` 包含省略号、合并多个段落、括号解释或模型归纳。
- 这意味着名为 `rawText` 的字段实际混入了摘要和推理。

期望行为：

- `rawText` 必须是材料逐字原文。
- 模型归纳只能放入 `fact`、`normalizedText` 或解释字段。
- 每条事实必须引用有效 `materialId`。
- 原文唯一匹配时生成精确 `location.start/end`。
- 原文无法定位、出现多处或需要跨段组合时，应使用多条证据，不能拼接成伪原文。
- artifact 的证据校验应达到正式 `materialEvidence` 相同或更严格的可追溯水平。

建议契约方向：

- 明确定义 `materialFacts` 每项的字段集合。
- 复用 `materialEvidence` 的证据结构，而不是另造宽松的 `rawText`。
- artifact 哈希必须在证据规范化和定位完成后计算。

验收标准：

- 篡改、概括、拼接或带省略号的 `rawText` 无法通过 prepare。
- 所有可定位原文均能从对应材料正文精确切片得到。
- artifact 中的解释与原文分字段保存。

### P0-5 prepare 报错必须区分草稿错误与内部错误

附件指出的现状：

```text
qc_report_prepare: missing required structure <KeyError/TypeError>
```

该错误无法告诉调用者具体缺少哪个路径，也把模型草稿问题与 Skill 自身异常混在一起。

期望行为：

- 缺字段时报告完整路径，例如：
  `inputScope.independentReview.artifact.ruleResults is required`
- 草稿字段缺失、类型错误、枚举非法使用稳定前缀：
  `qc_report_draft_error`
- 模块导入失败、脚本自身异常、序列化环境故障使用：
  `qc_report_internal_error`
- 内部错误不得被伪装成草稿错误。
- CLI 不输出 Python traceback，但开发测试必须保留可定位原因。

验收标准：

- 每个关键路径至少有一个单字段缺失测试。
- 错误类型和字段路径稳定可断言。
- 模型可依据错误直接修正对象，无需遍历整份约束文档猜测。

## 5. P1：建议同时修复项

### P1-1 检查规则原文与提取项的语义覆盖

本例规则 1001 原文至少包含：

1. 临床出现相应的脑部神经系统症状及体征。
2. 二级及以上医疗机构诊断为脑梗死或脑栓塞。
3. 住院治疗后仍遗有神经症状及体征，需要继续治疗。

当前 `ruleKeywordGuide` 只有两项：

- 医疗机构等级与诊断。
- 出院后遗留症状及继续治疗。

值得复核的真实维护问题：

- “临床出现相应的脑部神经系统症状及体征”没有独立提取项。
- 第一提取项是否真正覆盖“二级及以上医疗机构”，还是仅提取了诊断。
- 第三项中的“仍遗有症状”和“需继续治疗”是否被原子化、是否均有证据。

当前报告没有检查这些覆盖关系，却把四位编码和缺少 `keywordCode` 当成主要规则质量问题。

期望行为：

- 对规则原文做原子事实拆解。
- 为每个必须条件建立“原文条件—提取项”覆盖矩阵。
- 报告遗漏、合并过度、语义范围缩窄或扩大、AND/OR 错配。
- 兼容性字段 warning 与真正语义缺陷分开显示。

验收标准：

- 本例至少提示“临床症状及体征”可能缺少独立提取项。
- 不因四位规则码本身产生业务缺陷。
- 业务报告说明该缺项是否影响本次结论，而不是一律升级严重度。

### P1-2 自动生成可确定的证据位置

实际报告中的部分证据原文能在材料正文中找到，但 `location` 仍为 `null`，页面显示“未提供精确定位”。

期望行为：

- prepare 对每条证据在对应 `content` 中执行逐字查找。
- 唯一匹配时自动填写起止位置。
- 零次匹配时报草稿错误。
- 多次匹配时保留未知位置，并明确原因；后续可要求页码或章节辅助消歧。
- 不由模型手算字符偏移。

验收标准：

- 本例“出院情况：目前患者神志清楚……”可以自动定位。
- 自动位置能够被 renderer 重新切片校验。
- 原始文本修改后旧位置会失效并被拒绝。

### P1-3 业务页面减少内部字段和英文技术词

实际报告直接出现：

- `standardKind=structured_complete`
- `executable=true`
- `material_list`
- `referencedButMissing`
- `keywordCode`
- `Mode1`

这些内容可用于技术诊断，但不适合作为业务主文案。

期望行为：

- 主页面使用中文业务表述。
- 内部字段名、哈希、模式代码放入折叠的“技术校验信息”。
- 技术信息仍保留，不能为了可读性删除审计证据。
- 文本版也采用相同的业务文案层级。

示例：

- `referencedButMissing` → “原审核引用但未在已确认清单中找到的材料”
- `structured_complete` → “完整且可执行的结构化标准”
- `keywordCode` → “提取项编码”
- `Mode1` → “正式标准数据格式”

验收标准：

- 检查能力卡片和总体建议不再直接展示上述内部字段名。
- 技术人员仍可在折叠区域查看原值。
- HTML 与文本版表述一致。

### P1-4 优化材料清单显示

当前“材料”字段主要展示多个长数字 ID，业务人员很难区分。

期望行为：

- 主视图展示材料名称和数量。
- 建议格式：`住院病历-5（编号尾号 4083）`。
- 完整材料 ID、来源机构、材料类型放入可展开详情。
- 找不到材料名称时再回退到完整 ID。

验收标准：

- 六份材料可以在主页面快速区分。
- 不丢失完整 ID 的审计能力。
- 文本版和 HTML 版使用同一材料显示规则。

### P1-5 只读环境下的测试可移植性

现状：

- 生成型夹具测试默认向仓库 `tests/fixtures/generated/` 写入。
- 只读挂载环境会产生 `Read-only file system`，掩盖真实逻辑测试结果。

建议：

- 优先让生成脚本支持显式输出根或环境变量覆盖，例如 `QC_FIXTURE_ROOT`。
- 测试本身优先使用 `tempfile.TemporaryDirectory()`，不要依赖源码目录可写。
- 只有确实无法执行时才 skip；不要用 skip 掩盖普通代码错误。

验收标准：

- 在只读源码挂载、可写临时目录环境中，全部逻辑测试可运行。
- 开发者显式更新正式 fixtures 的命令仍可用。
- 只读限制与业务测试失败在输出中可区分。

## 6. P2：后续增强项

### P2-1 `--explain` 支持当前对象的非致命预检

现有 `--explain` 只输出静态规则。

期望行为：

- 无输入时继续输出静态约束。
- 提供草稿或正式对象时，输出当前对象的待修复清单。
- 尽量一次列出多个互不依赖的问题，而不是每次只暴露第一处。
- 明确区分“需要先 prepare”和“prepare 后仍不合法”。
- 输出不得泄漏材料正文、令牌或其他敏感值。

需要设计：

- CLI 形式，例如 `--explain <对象>`、`--check <对象>` 或独立预检命令。
- 是否复用 renderer 的 fail-fast 校验，还是新增收集式 validator。

验收标准：

- 能同时报告 standardKind 不一致、缺字段、哈希待生成和未执行检查待同步。
- 输出只包含字段路径、错误代码和安全修复提示。

### P2-2 逻辑追踪的契约形态

不建议只保存本地文件路径。路径在离线 HTML、ADP 和跨环境交付中不稳定。

推荐方向：

- 在 artifact 或 inputScope 中嵌入规范化 `logicTrace`。
- 记录 trace 的 SHA-256。
- trace 由 `evaluate_logic.py` 生成，不由模型手写。
- renderer 折叠展示顶层结果和各规则节点。

验收标准：

- 标准可执行且条件一致性检查完成时，缺少 trace 会被拒绝。
- trace 的规则集合、standardKind 和最终结果与 artifact 一致。
- 修改 ruleResults 后必须重新生成 trace 和摘要。

## 7. 明确不按原建议实施的内容

### 7.1 不用自填布尔值证明“真盲审”

`generatedInIsolatedContext=true` 只能证明对象中写了 true，不能证明执行真的隔离。

### 7.2 不用结果文本重叠率证明是否盲审

独立复核与原审核在正确时本来就可能高度一致；文本不同也不代表没有看过原审核。重叠率最多可做异常提示，不能作为可信边界。

### 7.3 不自动覆盖冻结产物的 `standardKind`

Skill 当前顺序已经是先 inspect，再进行独立复核。若后续分类变化，应增加 inventory revision、使旧确认失效并重新复核。

prepare 静默把 `inputScope.standardKind` 写回冻结 artifact 会改变已冻结语义，却让报告看似一致，破坏审计含义。正确行为是给出精确不一致错误并要求重新生成 artifact。

### 7.4 不因只读环境直接跳过全部生成型测试

优先把输出重定向到临时可写目录。skip 只作为平台完全不允许任何写入时的最后退路。

## 8. 推荐实施顺序

下次正式开工建议按以下顺序：

1. 从本次实际 HTML 提炼最小回归夹具。
2. 为 P0-1 至 P0-5 分别编写失败测试并确认能够复现。
3. 先修正 Skill 流程和报告契约，再修改 prepare 与 renderer。
4. 增加逻辑 trace 和 artifact 原文校验。
5. 完成根因去重及规则—提取项语义覆盖。
6. 调整业务 HTML 与文本版信息层级。
7. 修复只读测试可移植性和实时预检。
8. 运行全量测试、禁用词扫描、HTML 离线检查。
9. Chrome 验证目录与“查看”；ADP 只验证内容显示，不把其预览器锚点限制误判为 Skill 回归。

## 9. 最低回归用例矩阵

| 用例 | 预期 |
| --- | --- |
| 四位规则码、逻辑可解析、无 `keywordCode` | `structured_complete`，仅兼容性 warning，不产生业务问题 |
| 标准可执行但没有逻辑 trace | prepare 或 render 拒绝正式输出 |
| 错误材料 ID，但原文存在于另一材料 | 只生成一条证据溯源根因问题 |
| artifact `rawText` 含省略号或改写 | 拒绝 |
| artifact 原文唯一匹配 | 自动生成位置 |
| artifact 原文多处匹配 | 要求消歧或明确未知位置原因 |
| 同一次上下文中复核并读取原审核，却声明 `isolated_blind` | 拒绝或降级为非盲 |
| 规则原文含三个必须事实但提取项只覆盖两个 | 报告缺少提取项 |
| 只读源码目录、可写临时目录 | 全部逻辑测试正常执行 |
| 业务 HTML | 主页面不直接暴露内部字段名和完整哈希 |

## 10. 完成定义

只有同时满足以下条件，第二轮优化才算完成：

- 本次实际案例对应的最小回归夹具通过。
- 唯一问题数与根因数一致。
- 标准兼容性 warning 不再误升级为规则缺陷。
- 可执行标准实际生成并展示逻辑追踪。
- 冻结复核产物中的每条原文可追溯。
- 盲审命名与可验证执行方式一致。
- 规则原文与提取项覆盖关系经过检查。
- 业务页面减少技术噪音但保留审计信息。
- 只读环境不会使逻辑测试误红。
- 全量自动化测试、内容扫描、HTML 离线检查和浏览器验收全部通过。
