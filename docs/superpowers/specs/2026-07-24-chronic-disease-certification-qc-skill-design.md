# 门诊慢特病认定标准与审核质控 Skill 设计

## 1. 目标

在 AIRS 仓库一级目录创建一个平台无关的 Skill：

```text
/Users/Tristan/TristansDevelop/TristanProject/AIRS/chronic-disease-certification-qc
```

Skill 对用户提供两个工作模式：

1. 根据病种认定信息生成门诊慢特病结构化认定标准；
2. 根据患者申请材料、智能审核结果以及用户能够提供的认定标准，生成智能审核质控报告。

Skill 对外只有一个入口，内部将两个工作模式隔离实现，并共享数据解析、规则语义、证据状态、逻辑计算和 HTML 渲染能力。

## 2. 交付物

### 2.1 模式 1：生成结构化认定标准

固定生成：

```text
<病种>-certification_list-<版本>.json
<病种>-认定标准可视化-<版本>.html
```

JSON 面向门诊慢特病智能审核系统，HTML 面向业务人员。

JSON 是唯一事实源。HTML 必须由通过校验的 JSON 生成，不允许独立维护另一份规则内容。

### 2.2 模式 2：生成质控报告

固定生成：

- 文本版：直接返回给用户；
- HTML 版：写入本地单文件报告。

文本和 HTML 必须由同一份内部质控对象渲染，结论、问题数量、严重程度和证据引用必须一致。

## 3. 非目标

第一版不包含：

- 调用或配置任何特定第三方工作流平台；
- 患者信息脱敏或外发版报告；
- 未经校准的数字质控评分；
- 自动替业务人员决定存在关键歧义的正式认定口径；
- 在未取得用户同意时生成含关键歧义的正式标准；
- 使用未提供的政策、医学知识或经验补造准入条件；
- 承诺覆盖所有医学场景下的临床判断准确性。

## 4. 平台无关约束

Skill 的说明、界面元数据、参考资料、脚本、模板和测试样例不得包含特定第三方工作流平台的名称、接口、环境、节点、密钥或专属运行概念。

所有用户可见表述统一使用：

- 门诊慢特病结构化认定标准；
- 门诊慢特病智能审核系统；
- 智能审核系统兼容的标准数据格式；
- 智能审核结果；
- 审核运行记录。

实现验收时必须对 Skill 全目录执行全文检查。需要检查的平台专有词由 Skill 外部的验证命令传入，不在 Skill 内固化。

## 5. Skill 结构

目录设计为：

```text
chronic-disease-certification-qc/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── certification-contract.md
│   ├── structuring-rules.md
│   ├── qc-rubric.md
│   ├── input-adapters.md
│   └── report-contract.md
├── scripts/
│   ├── inspect_standard.py
│   ├── validate_certification.py
│   ├── evaluate_logic.py
│   ├── render_certification_html.py
│   ├── render_qc_html.py
│   └── check_skill_content.py
├── assets/
│   ├── certification-template.html
│   └── qc-report-template.html
└── tests/
    ├── fixtures/
    └── test_*.py
```

职责边界：

- `SKILL.md`：识别意图、选择模式、执行输入确认和用户批准门禁；
- `references/`：保存数据契约、语义规范、质控口径和报告契约；
- `scripts/`：执行确定性解析、结构校验、逻辑计算和 HTML 渲染；
- `assets/`：保存两个离线单文件 HTML 模板；
- `tests/`：保存结构测试、合成语义案例、变异案例和渲染测试。

详细知识不重复写入 `SKILL.md`。`SKILL.md` 只保留核心流程以及何时读取对应参考文件的导航。

## 6. 路由与输入预检

### 6.1 意图路由

用户请求生成、整理、维护或可视化病种认定标准时，进入模式 1。

用户请求复核、检查、质控或分析智能审核结果时，进入模式 2。

当一次请求同时包含两种任务时，先生成并确认正式认定标准，再使用该标准执行质控。

### 6.2 输入适配

Skill 必须兼容：

- 用户直接粘贴的自然语言；
- Markdown 或纯文本文件；
- 中文表格转写内容；
- JSON 对象；
- JSON 字符串；
- 带常见外层包装的 JSON；
- 一个或多个患者材料文件；
- 只有最终结论的审核结果；
- 包含逐规则判断、证据和疑点的完整审核结果。

解析后的内部输入统一为：

```text
MaterialBundle
StandardBundle
AuditResultBundle
```

后续语义分析和报告生成不得直接依赖原始输入的包装形式。

### 6.3 模式 2 输入确认

模式 2 在生成报告前必须展示简短输入清单，并让用户确认是否漏传：

- 患者材料；
- 中文或结构化认定标准；
- 审核过程；
- 最终结论；
- 审核结果中引用但尚未提供的材料。

若用户表示漏传，等待补充后重新预检。

若用户确认没有更多内容，按当前输入能够支持的质控维度继续，不要求普通用户提供结构化 JSON。

## 7. 模式 1：结构化认定标准生成

### 7.1 输入

必需输入：

- 病种名称；
- 病种编码；
- 认定标准原始信息。

建议输入：

- 版本号；
- 来源文件或政策名称；
- 生效地区；
- 生效日期；
- 原始章节或条款位置。

病种编码必须以两位数字结尾。无法获得合规编码时，不生成正式 JSON，也不编造编码。

版本确定顺序：

1. 使用用户明确提供的版本号；
2. 从来源文件名、标题或正文中提取；
3. 仍无法提取时，使用生成日期形成 `VYYYYMMDD`。

使用生成日期时，必须在生成摘要和 `meta.description` 中说明该版本号来自生成日期，不代表政策发布日期。

### 7.2 正式 JSON 契约

正式 JSON 顶层直接为：

```json
{
  "meta": {},
  "ruleRepository": [],
  "logicTopology": {}
}
```

它作为门诊慢特病智能审核系统的认定标准对象使用，不增加当前系统无法稳定消费的正式字段。

`meta` 至少包含：

```json
{
  "version": "VYYYYMMDD",
  "chronicDiseaseName": "病种名称",
  "chronicDiseaseCode": "病种编码",
  "createdAt": "YYYY-MM-DD",
  "description": "版本说明",
  "sourceFile": "来源文件或政策"
}
```

每条 `ruleRepository` 规则至少包含：

```json
{
  "ruleCode": "01001",
  "ruleContent": "认定规则",
  "ruleSource": "规则来源",
  "experience": "",
  "ruleKeywordGuide": [],
  "sourceRuleContent": "对应的认定标准原文",
  "sourceMdFile": "来源文件名",
  "sourceSection": "来源章节"
}
```

每条 `ruleKeywordGuide` 至少包含：

```json
{
  "keywordCode": "01001001",
  "dataType": "enum",
  "required": true,
  "keywordContent": "原子提取任务、肯定证据、反向证据、无法判断边界和优先材料位置",
  "enumOptions": ["是", "否", "无法判断"]
}
```

兼容性限制：

- `dataType` 只允许 `enum` 或 `string`；
- `enum` 必须有非空 `enumOptions`；
- `string` 的 `enumOptions` 必须为 `[]`；
- `logicTopology` 只允许 `GROUP` 和 `RULE_REF`；
- `GROUP.operator` 只允许 `AND` 和 `OR`；
- 正式 JSON 不加入数值约束、时间窗口等扩展字段；
- 数值、单位、比较符、时长和次数要求写入 `ruleContent` 与 `keywordContent`。

规则编码：

```text
ruleCode = 病种编码末两位 + 三位规则序号
keywordCode = ruleCode + 三位提取项序号
```

### 7.3 生成阶段

第一阶段生成临时标准：

1. 整理来源；
2. 识别病种、版本、章节和来源；
3. 区分准入条件与辅助细则；
4. 将准入条件拆成独立规则；
5. 将复合规则拆成原子提取项；
6. 识别 AND、OR 和嵌套路径；
7. 使用 `R001` 等临时编码；
8. 每条规则绑定对应来源原文。

生成时只使用用户提供的信息。病种名称只提供上下文，不得触发额外医学条件。

### 7.4 独立复核阶段

重新对照原始信息检查：

- 是否遗漏原文条件；
- 是否增加原文没有的条件；
- 数值、单位、时长、次数或机构等级是否改变；
- AND/OR 是否正确；
- 提取项是否缺失；
- 提取项是否保持原子性；
- 辅助细则是否被错误提升成准入规则；
- 来源之间是否冲突；
- 规则是否存在无法执行的含糊表达。

能依据原文唯一确定的错误可以自动修正。不能唯一确定的内容进入待确认事项。

### 7.5 歧义与批准门禁

以下属于阻断性歧义：

- 无法确定 AND 或 OR；
- 阈值、单位、时长或次数不明确；
- 适用范围不明确；
- 多个来源相互冲突；
- 无法判断某段内容是准入条件还是辅助细则；
- 无法确定排除条件、例外条件或共同条件；
- 病种编码冲突；
- 不同解释会形成不同审核结论。

遇到阻断性歧义时：

1. 尽量逐项向用户问清；
2. 根据回答整理拟采用的规则方案；
3. 展示拟采用的规则、提取项和逻辑关系；
4. 取得用户明确同意；
5. 同意后才生成正式 JSON 和 HTML。

用户无法确认时，停止在待确认规则方案，不生成正式文件。

### 7.6 确定性校验与渲染

Python 脚本负责：

- 生成正式编码；
- 校验必填字段和字段类型；
- 校验 `enumOptions`；
- 校验编码唯一性；
- 校验逻辑树结构；
- 校验规则引用完整性；
- 校验来源字段；
- 写入正式 JSON；
- 从正式 JSON 生成 HTML；
- 重新读取产物完成交付校验。

JSON 校验失败时不得生成业务可用 HTML，也不得将半成品标记为正式版本。

### 7.7 HTML 内容

HTML 为离线可打开的单文件，展示：

- 病种、编码、版本和来源；
- AND/OR 逻辑拓扑；
- 规则摘要；
- 政策依据；
- 来源分项；
- 认定标准原文；
- 提取项说明；
- 数据类型、是否必需和枚举选项；
- 完整数据结构折叠区；
- 规则维护或结构告警。

页面不得截断规则和提取项内容。

## 8. 模式 2：智能审核质控

### 8.1 输入形态不是质控门槛

普通用户通常提供中文表格或自然语言认定标准。此类输入是正常输入，不视为错误，也不要求用户先转换成结构化 JSON。

根据输入决定每个质控维度是否可执行：

| 输入 | 可执行质控 |
| --- | --- |
| 材料 + 审核结论 | 材料事实、证据忠实度、过度推理、结果内部一致性 |
| 材料 + 中文标准 + 审核结果 | 增加独立规则判断、逻辑复核、错误放行或错误拒绝风险 |
| 材料 + 不完整结构化标准 + 审核结果 | 增加结构缺陷定位和可用部分复核 |
| 材料 + 完整结构化标准 + 审核结果 | 增加提取项维护质量、编码、字段、逻辑树和来源追溯检查 |
| 再提供原始政策来源 | 增加结构化标准与政策原文的一致性检查 |

报告必须逐项列明已执行和未执行的质控维度及原因。

### 8.2 标准识别

结构化标准由 Python 脚本判断：

- 是否可解析；
- 是否有常见外层包装；
- 是否存在 `meta`、`ruleRepository` 和 `logicTopology`；
- 规则与提取项字段是否完整；
- 编码是否唯一；
- 枚举字段是否合法；
- 逻辑树是否可执行；
- 规则引用是否完整；
- 来源追溯字段是否存在。

结构化标准完整度分为：

1. 结构完整；
2. 可执行完整；
3. 可追溯完整；
4. 来源一致。

没有原始政策或完整来源原文时，不得宣称已经检查来源一致性。

### 8.3 不完整结构化标准

不完整标准不得简单报错退出。报告先列出精确字段路径、问题和影响，例如：

```text
ruleRepository[1].ruleKeywordGuide 为空
logicTopology 未引用规则 01003
规则 01002 缺少 sourceRuleContent
```

随后使用仍然有效的部分继续质控：

- 有效规则继续核对；
- 缺少提取项但仍有 `ruleContent` 时进行有限语义复核；
- 逻辑树不完整时不输出确定性的整体重算结论；
- 报告标明每项判断的能力限制。

### 8.4 中文或自然语言标准

Skill 将中文标准转换成本次质控专用的临时规则模型：

```json
{
  "sourceType": "natural_language",
  "status": "provisional",
  "rules": [],
  "logicTopology": {},
  "ambiguities": [],
  "assumptions": []
}
```

临时模型要求：

- 只使用用户提供的文字；
- 拆出准入条件、原子事实和 AND/OR；
- 保留每条临时规则对应的原文；
- 不补充医学条件；
- 使用 `TMP-R001` 等临时编码；
- 不作为正式结构化标准文件交付；
- 语义含糊时记录不同解释。

若不同解释会改变质控结论，报告分别展示各解释下的结果，并标记需要人工确认。

### 8.5 证据状态

内部证据状态固定为：

- `SUPPORTED`：材料明确支持；
- `CONTRADICTED`：材料明确给出反向证据；
- `NOT_FOUND`：材料中没有找到相关内容；
- `INSUFFICIENT`：存在相关信息，但不足以证明；
- `CONFLICTED`：不同材料之间相互矛盾；
- `NOT_APPLICABLE`：当前路径不适用。

规则结果固定为：

- 满足；
- 不满足；
- 无法判断；
- 不适用。

报告必须区分整份材料缺失、证据未找到、证据不足、明确反向证据和材料冲突。

### 8.6 盲审后对比

为降低原审核结果带来的确认偏差，完整语义质控采用两阶段：

第一阶段独立复核：

1. 只读取患者材料和判定标准；
2. 建立材料事实和证据索引；
3. 独立判断每条规则；
4. 独立计算最终结果。

第二阶段差异分析：

1. 读取原智能审核结果；
2. 比较证据；
3. 比较提取值；
4. 比较逐条结论；
5. 比较最终结论；
6. 定位问题发生在证据提取、规则判断、逻辑合并或规则维护层。

没有标准时，先建立患者材料事实索引，再逐条验证原审核结果声称的证据、缺失项和事实。

### 8.7 质控维度

#### 材料缺失判断准确性

检查原审核结果声称缺少的材料或证据在患者材料中是否存在，并区分：

- 确实缺失；
- 误报缺失；
- 部分存在但证据不足。

#### 证据提取准确性

检查：

- 引用原文是否真实存在；
- 原文与提取值是否同义；
- 否定、疑似、既往史、排除诊断是否被误识别；
- 一次性治疗是否被误识别成长期治疗；
- 上位概念是否被误识别成具体分型；
- 患者、日期、医院和材料是否对应正确。

#### 过度推理

材料只能证明其明确表达的事实。不得依靠疾病常识、常见治疗方案、药物用途或概率关系补全缺失事实。

#### 审核条件与结论一致性

检查：

- 同一事实在不同位置取值矛盾；
- 理由与规则结果矛盾；
- 必需条件与最终结论矛盾；
- OR 路径满足后仍被其他不适用路径否决；
- 疑点、建议和最终结论矛盾；
- 不同规则对同一证据解释矛盾。

#### 规则维护质量

结构质量：

- 提取项、编码、枚举或来源字段缺失；
- 逻辑树引用错误；
- 编码重复。

语义质量：

- 提取项不原子；
- 肯定、反向或无法判断边界缺失；
- 规则与提取项不一致；
- 提取项重复、矛盾或含糊。

完整性质量：

- 原文必要事实没有对应提取项；
- 增加原文没有的条件；
- AND/OR 结构错误；
- 准入路径遗漏；
- 辅助细则被错误提升为准入规则。

### 8.8 证据溯源

每项质控判断尽量保留：

```json
{
  "materialId": "M001",
  "materialName": "出院记录",
  "page": 2,
  "section": "出院诊断",
  "rawText": "患者规律血液透析治疗3年",
  "normalizedText": "",
  "location": {
    "start": 1280,
    "end": 1295
  }
}
```

约束：

- `rawText` 优先保留原文；
- OCR 清洗内容不得伪装成原始文字；
- 无法精确定位时不得生成虚构引文；
- 同名患者、多次就诊和多份材料必须区分；
- 患者、日期、医院不一致时主动告警。

### 8.9 问题结构

每个质控问题使用统一内部结构：

```json
{
  "category": "证据提取准确性",
  "issueType": "提取值错误",
  "severity": "high",
  "ruleCode": "01002",
  "keywordCode": "01002001",
  "modelClaim": "患者未提供长期透析证明",
  "materialEvidence": [],
  "qcFinding": "材料中已存在长期透析证据，缺失判断不成立",
  "possibleImpact": "可能导致错误拒绝",
  "impactOnFinalResult": "potentially_changed",
  "riskDirection": "false_rejection",
  "recommendation": "修正提取项判断并重新计算规则和最终结论",
  "confidence": "high"
}
```

`impactOnFinalResult` 取值：

- `changed`；
- `potentially_changed`；
- `unchanged`；
- `unknown`。

`riskDirection` 取值：

- `false_approval`；
- `false_rejection`；
- `both`；
- `none`。

### 8.10 结论口径

原审核结果可靠性：

- 可靠；
- 基本可靠；
- 存在重大疑点；
- 不可靠；
- 无法确定。

风险方向：

- 错误放行风险：本应不通过，却被判为通过；
- 错误拒绝风险：本应通过，却被判为不通过；
- 局部判断错误：部分规则判断有误，但未改变最终结论；
- 仅影响规则质量；
- 暂时无法判断；
- 未发现明显风险。

建议动作：

- 无需处理；
- 补充患者材料；
- 补充判定标准；
- 修正规则提取项；
- 修正逻辑关系；
- 重新执行智能审核；
- 转人工复核；
- 由业务人员确认标准口径。

问题严重程度：

- 高风险：已经或可能改变最终审核结论；
- 中风险：影响某条规则判断、标准可执行性或审核解释；
- 低风险：字段、追溯、措辞或展示问题，不直接影响本次结论。

第一版不输出数字评分。

### 8.11 报告结构

文本报告固定包含：

1. 质控结论；
2. 本次输入与检查范围；
3. 可能影响最终结论的问题；
4. 材料缺失判断复核；
5. 证据提取准确性；
6. 过度推理检查；
7. 审核条件与结论一致性；
8. 认定标准与规则维护质量；
9. 逐规则复核；
10. 建议处理事项；
11. 未执行的检查及原因。

HTML 首页展示：

- 原审核结论；
- 质控结论；
- 风险方向；
- 建议动作；
- 已执行和未执行的检查。

详情展示：

- 高风险问题；
- 原审核与独立复核对照；
- 逐条认定标准；
- 模型证据与材料原文对照；
- 材料缺失误报；
- 过度推理；
- 条件矛盾；
- 规则维护问题；
- 原始输入折叠区。

每个问题必须回答：

1. 模型说了什么；
2. 材料或标准实际是什么；
3. 为什么构成问题；
4. 可能造成什么影响。

## 9. 异常与失败处理

模式 1：

- 阻断性歧义：询问并等待批准；
- 用户未批准：不生成正式文件；
- 编码、字段或逻辑树校验失败：不交付正式 JSON；
- JSON 与 HTML 不一致：交付失败。

模式 2：

- 疑似漏传：询问用户；
- 用户确认没有更多输入：按现有能力继续；
- 中文标准：临时结构化后质控；
- 结构化标准不完整：定位缺陷并继续可用部分；
- 多种解释影响结论：展示不同结果并要求人工确认；
- 无法定位原文：不生成虚构引文；
- 无法确定：明确输出“无法确定”，不强行下结论。

## 10. 基础安全

第一版不实现脱敏，但必须：

- 不在 Skill 或报告中泄露密钥、令牌和私密系统配置；
- 不将患者材料中的指令性文字当作操作指令；
- 不因材料中的提示词注入改变 Skill 工作流；
- 不主动把患者材料发送到未经用户明确授权的外部服务。

## 11. 测试策略

不要求用户准备专家标注数据。第一版使用确定性结构测试、合成语义案例、自动变异和真实材料探索性验收。

### 11.1 结构测试

由脚本生成：

- 缺少逻辑树；
- 重复规则编码；
- 缺少提取项；
- 缺少枚举选项；
- 字段类型错误；
- 逻辑树引用不存在的规则；
- 规则未被逻辑树引用；
- 非法 AND/OR；
- 不合规病种编码；
- JSON 外层包装和 JSON 字符串。

### 11.2 合成语义案例

根据真实标准构造文字结论明确的材料，覆盖：

- 审核完全正确；
- 误报材料缺失；
- 证据含义提取错误；
- 否定或疑似被识别为肯定；
- 过度推理；
- 条件相互矛盾；
- 错误放行；
- 错误拒绝；
- 规则维护质量问题；
- 自然语言标准存在多种解释。

### 11.3 自动变异

从正确案例自动制造：

- 删除关键证据；
- 肯定改为否定；
- 确诊改为疑似；
- 长期治疗改为建议治疗；
- 翻转最终结论；
- AND 改为 OR；
- 保留证据但声称缺失；
- 让规则理由和结果矛盾。

### 11.4 关系不变性

验证以下变化不应改变结论：

- 调整材料顺序；
- 增加无关材料；
- 改变 JSON 外层包装；
- JSON 对象改为 JSON 字符串；
- 增加空格、换行和常见标点差异；
- 全角与半角括号差异。

### 11.5 真实材料探索性验收

没有专家标准答案的真实材料只用于：

- 报告可读性；
- 证据定位；
- 明显误报发现；
- 大材料输入稳定性；
- HTML 承载能力。

真实材料不作为自动化医学正确率的通过或失败依据。

第一版目标规模：

- 20 至 30 个结构测试；
- 12 至 15 个合成语义案例；
- 8 至 10 个自动变异案例；
- 3 至 5 个真实材料探索性案例；
- 2 个模式 1 生成基准案例；
- 2 个必须询问用户的歧义案例。

## 12. 验收标准

### 12.1 Skill 验收

- Skill 位于 AIRS 一级目录；
- Skill 元数据能准确触发两种工作模式；
- `SKILL.md` 保持精简并正确导航参考文件；
- Skill 全目录不含指定的平台专有词；
- Skill 基础格式校验通过；
- 所有确定性脚本具有可运行测试。

### 12.2 模式 1 验收

- 正式 JSON 可解析；
- 顶层结构和字段兼容门诊慢特病智能审核系统；
- 编码正确且唯一；
- 每条规则至少有一条提取项；
- 枚举字段完整；
- 逻辑树引用完整；
- 来源可追溯；
- 阻断性歧义未经用户批准时不生成正式文件；
- HTML 与 JSON 内容一致；
- HTML 可离线打开且不截断规则内容。

### 12.3 模式 2 验收

- 报告前完成输入清点和用户确认；
- 不要求普通用户提供结构化 JSON；
- 中文标准能够生成临时规则并参与质控；
- 报告逐项说明已执行和未执行的检查；
- 能区分材料缺失、证据未找到、证据不足、反向证据和材料冲突；
- 能发现误报缺失、证据错引、过度推理和内部矛盾；
- 完整标准输入时能独立复核规则和逻辑；
- 问题能定位到规则、提取项、材料和原文；
- 风险方向使用“错误放行风险”和“错误拒绝风险”；
- 文本与 HTML 结论一致；
- 无法确定时不强行给出确定结论。

## 13. 后续实施顺序

用户审阅并批准本设计后，再编写实施计划。实施计划按以下顺序展开：

1. 初始化 Skill 目录和界面元数据；
2. 编写正式数据契约与输入适配规范；
3. 实现结构检查、逻辑计算和 HTML 渲染脚本；
4. 编写模式 1 工作流；
5. 编写模式 2 工作流；
6. 构造测试夹具并运行回归测试；
7. 使用现有真实资料做探索性验收；
8. 完成全文检查、Skill 校验和最终交付。
