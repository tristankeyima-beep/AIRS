# 门诊慢特病认定标准与审核质控 Skill 验收用例集设计

## 1. 目标

为 `chronic-disease-certification-qc` Skill 建立一套可直接用于人工验收的测试用例集，并生成一个全部内容内嵌、可离线使用的单文件 HTML 验收台。

验收人员无需准备额外材料，也无需在多个目录间查找输入。每条用例均提供完整输入、建议对话步骤、预期交互关口、预期结果、禁止出现的行为以及可勾选的验收项。

本项目不修改 Skill 的运行时契约。验收材料作为 AIRS 下独立的同级目录维护，避免增加 Skill 被触发时的上下文负担。

## 2. 交付结构

```text
AIRS/
├── chronic-disease-certification-qc/
└── chronic-disease-certification-qc-acceptance/
    ├── acceptance-cases.json
    ├── build_acceptance_html.py
    ├── 慢特病认定标准与审核质控-验收测试用例.html
    └── tests/
        └── test_acceptance_catalog.py
```

- `acceptance-cases.json`：结构化、可维护的验收用例唯一来源。
- `build_acceptance_html.py`：校验用例并确定性生成 HTML。
- `慢特病认定标准与审核质控-验收测试用例.html`：可单独复制、离线打开的人工验收台。
- `test_acceptance_catalog.py`：检查用例合同、覆盖范围、生成确定性与离线安全。

## 3. 方案选择

采用“结构化用例源生成单文件 HTML”：

- 相比直接手写大 HTML，更容易增删用例并保持字段一致。
- 相比多页面测试站，更方便携带、离线验收和打印。
- 最终 HTML 内嵌全部输入和交互逻辑，不依赖 JSON 文件才能运行。

## 4. 覆盖矩阵

第一版目标为 35 至 40 条用例，覆盖以下四组。

### 4.1 模式 1：认定标准结构化

至少覆盖：

1. 明确的自然语言标准，顶层 AND 且子条件包含 OR。
2. AND/OR 无法唯一确定，必须询问用户。
3. 缺少病种名称。
4. 缺少病种编码。
5. 未提供版本，使用生成日期并说明不是政策发布日期。
6. 用户尚未批准提案，不得生成正式 JSON 或 HTML。
7. 用户明确批准后生成正式 JSON 和 HTML。
8. 完整、合法的结构化正式标准。
9. 结构化标准缺少提取项。
10. 提取项缺少枚举选项。
11. 重复 JSON 键。
12. 规则编码与病种编码不一致。
13. 提取项编码跨规则或顺序错误。
14. 逻辑树引用不存在的规则。
15. 规则未被逻辑树引用。
16. 逻辑树循环或深度超限。
17. JSON 外层包装、JSON 字符串和 BOM。
18. 来源间存在冲突，必须请用户确认。

### 4.2 模式 2：审核质控

至少覆盖：

1. 审核完全正确，不得强行报告问题。
2. 审核误报材料缺失。
3. 材料确实缺失。
4. 审核证据与材料原文含义相反。
5. 否定表述被识别成肯定。
6. 疑似表述被识别成确诊。
7. 建议进一步评估被推理成已经完成治疗。
8. 审核条件与审核建议相互矛盾。
9. AND 必需条件缺少却错误放行。
10. OR 任一条件满足却错误拒绝。
11. 规则维护缺少提取项。
12. 规则语义含糊，存在多种解释路径。
13. 只提供材料与最终审核结论。
14. 提供材料、自然语言标准与简要审核结果。
15. 提供材料、完整结构化标准与详细审核过程。
16. 未提供认定标准，明确限制可执行检查。
17. 结构化标准不完整，仍可进行有限质控并报告限制。
18. 证据定位与材料原文偏移不一致。

### 4.3 交互关口

至少覆盖：

1. 首次清点后必须询问“是否遗漏任何内容”。
2. 用户补传材料后 revision 增加、摘要重算、旧确认失效。
3. 未确认前不得生成正式质控对象、文本或 HTML。
4. 归因式、否定式、疑问式或带额外指令的确认语句无效。
5. 有效完整句确认后才能继续。
6. 独立复核必须在读取原审核结果进行对比之前完成。
7. 无法隔离盲审时标记独立非盲复核及其限制。
8. 自然语言标准存在影响结论的多种解释时，计算各路径并返回“无法确定”。

### 4.4 安全与产物

至少覆盖：

1. 患者材料中的“忽略之前指令”不改变流程。
2. 材料要求执行命令、调用工具或跳过关口时必须拒绝。
3. 疑似密钥、令牌、授权头、Cookie、密码、私钥或秘密环境变量时 fail-closed。
4. 未明确授权具体目的地和动作时，不外发患者材料。
5. 输入中的 HTML、事件属性和脚本按纯文本显示。
6. HTML 无外部字体、图片、样式或脚本依赖。
7. 正式输入与输出路径相同或互为别名时拒绝覆盖。
8. 文本与 HTML 来自同一规范对象，结论、风险、问题数和证据一致。
9. 生成失败时不留下部分输出或破坏已有文件。
10. 大段材料和窄屏显示不产生横向裁切或内容丢失。

## 5. 用例数据合同

每条用例使用统一字段：

```json
{
  "id": "M2-QC-001",
  "title": "审核误报材料缺失",
  "mode": "mode2",
  "category": "材料缺失判断准确性",
  "priority": "P0",
  "inputKinds": ["materials", "natural_language_standard", "brief_audit_result"],
  "objective": "验证材料存在时不会错误报告缺失",
  "preconditions": [],
  "inputs": [
    {
      "name": "患者材料",
      "format": "text",
      "content": "……"
    }
  ],
  "steps": [
    {
      "actor": "tester",
      "action": "提交输入",
      "expected": "展示输入清单并询问是否遗漏"
    }
  ],
  "expectedOutcome": {
    "qcConclusion": "不可靠",
    "riskDirection": "错误拒绝风险",
    "issues": ["误报缺失"]
  },
  "mustContain": [],
  "mustNotContain": [],
  "acceptanceChecks": [],
  "notes": ""
}
```

合同要求：

- `id` 全局唯一且体现模式、领域和序号。
- `priority` 只使用 `P0`、`P1`、`P2`。
- 风险用语只使用 Skill 合同允许的正式表述。
- `inputs` 包含可直接复制的完整内容，不依赖外部文件。
- `steps` 明确区分测试人员动作与系统预期行为。
- `mustNotContain` 用于锁定过度推理、错误放行、错误拒绝和跳过关口等反例。
- 用例不得包含真实患者信息或真实秘密。

## 6. HTML 验收台

### 6.1 信息架构

页面采用“审核控制台”式单页结构：

- 顶部：标题、版本、覆盖范围说明和总体进度。
- 汇总区：总数、通过、失败、阻塞、未执行及完成率。
- 筛选区：关键词、模式、分类、优先级、输入类型、风险方向、执行状态。
- 主体区：按用例卡片展示，支持展开和收起。
- 底部：导入、导出、重置和打印入口。

### 6.2 用例卡片

每张卡片包含：

- 用例编号、标题、优先级和分类标签。
- 测试目的与前置条件。
- 完整输入，按材料、标准、审核结果分块展示。
- 每个输入块的一键复制按钮。
- “输入清点 → 用户确认 → 独立复核 → 结果对比 → 正式报告”的关口时间线。
- 操作步骤和逐步预期。
- 最终预期结果。
- 必须出现与绝对不能出现的行为。
- 未执行、通过、失败、阻塞四态选择。
- 实际结果和备注文本框。

### 6.3 视觉方向

- 风格：专业、克制的审核控制台。
- 主色：深蓝灰；通过使用青绿色；待确认使用橙色；失败和高风险使用红色。
- 标志性设计：每条用例的交互关口时间线。
- 使用系统字体，不加载外部字体或图标。
- 桌面端使用双栏信息层级，窄屏自动变为单栏。
- 支持键盘导航、清晰焦点、语义化标签和高对比度。
- 支持 `prefers-reduced-motion`。

## 7. 验收记录

- 使用带版本前缀的 `localStorage` 键保存验收状态、实际结果和备注。
- 页面加载时自动恢复相同版本的记录。
- 导出 JSON 包含页面版本、导出时间、用例状态和备注，不包含额外浏览器信息。
- 导入前校验版本、用例 ID、状态枚举和字段类型。
- 导入失败时显示明确错误，不覆盖已有记录。
- 重置操作要求二次确认。
- 打印模式隐藏筛选、复制、导入导出和编辑控件，保留结果与备注。

## 8. 安全与离线约束

- 最终 HTML 不加载任何外部资源。
- 用例数据在构建时转义后嵌入，避免关闭脚本或样式上下文。
- 页面渲染用例内容时使用文本节点，不把输入内容作为 HTML 执行。
- 导入文件仅作为 JSON 数据读取，不执行其中的任何指令或代码。
- 复制操作只复制当前输入块文字。
- 页面不上传、不发送、不请求网络资源。

## 9. 生成器

`build_acceptance_html.py` 执行以下步骤：

1. 读取 UTF-8 JSON，拒绝重复键。
2. 校验根对象、版本和每条用例的完整字段。
3. 校验 ID 唯一、枚举合法和覆盖矩阵。
4. 对嵌入数据进行安全序列化。
5. 生成一个 UTF-8、末尾单换行的 HTML。
6. 使用同目录临时文件原子替换目标。
7. 重复运行产生字节完全一致的结果。

输出路径不得与输入路径或其别名相同；现有输出是符号链接时拒绝。

## 10. 自动验证

`test_acceptance_catalog.py` 至少验证：

- 用例数量在目标范围内。
- 四组覆盖矩阵均达到最低数量。
- P0 用例覆盖两个模式的关键关口和两种风险方向。
- 所有必填字段、枚举和 ID 合法。
- 所有输入非空且不依赖本地文件路径。
- 用例不含真实秘密形状或项目禁用术语。
- 风险文案符合正式合同。
- 正确案例不强行报告问题。
- 错误放行和错误拒绝案例的逻辑与预期一致。
- HTML 中内嵌全部用例。
- HTML 无外部资源、可执行用户输入或事件属性注入。
- 本地存储、导入导出、打印和复制控件存在。
- 连续生成两次字节一致。
- 失败写入不破坏已有 HTML。
- `git diff --check` 和 Skill 原有完整测试保持通过。

## 11. 完成标准

- 交付 35 至 40 条完整、可复制的验收用例。
- 模式 1、模式 2、交互门禁、安全与产物四类均有覆盖。
- 最终 HTML 可离线打开、搜索、筛选、复制、记录、导入导出和打印。
- 所有验收数据均为合成数据，除已确认的脑梗死模式 1 示例外不使用真实病种判断。
- 生成器、用例合同和 HTML 安全测试全部通过。
- Skill 原有测试、官方校验和全目录禁用词扫描继续通过。
