# 申请材料预检与补件清单 Flash Skill 设计

## 1. 目标与边界

新增独立 Skill `chronic-disease-material-precheck-flash`。它依据用户确认采用的门诊慢特病认定标准，对已确认的申请材料进行条件—证据预检，生成补充信息或补件建议的 JSON 与离线 HTML。

它不是正式资格审核：不输出“通过”或“不通过”，不评价原审核结果，不依据未提供的医学知识或政策要求补造材料要求。

## 2. 标准输入与采用门禁

标准可来自：

1. 用户直接提供的自然语言标准或政策原文。
2. 用户提供的知识库检索结果中的候选标准。
3. 审核标准生成 Skill 已确认交付的结构化标准 JSON。

自然语言标准或多个候选来源时，先盘点病种、来源、版本和候选差异；检查 AND/OR、阈值、单位、时长、次数、范围、排除项、共享前提及来源冲突。存在影响条件含义的歧义时，停在待确认摘要。只有用户明确确认采用的标准及规则解释后，才进入材料预检。

结构化标准 JSON 只能在其自身已经确认、`schemaVersion=flash-1.0` 且 `mode=certification` 时直接使用；原始标准来源仍需随本次成果保留。

## 3. 材料确认与预检流程

1. 展示材料清单，用户确认是否遗漏内容；未明确确认时不生成正式成果。
2. 以已确认标准的每条规则、提取项和逻辑关系为准，逐项定位材料证据。
3. 输出四种预检状态：`已定位证据`、`信息不足`、`未定位证据`、`材料形式待确认`。
4. 汇总补充项并标明其对应规则、依据、优先材料位置和说明；不把“未定位证据”写成患者未提交材料的事实。
5. 生成 JSON 并注入固定离线 HTML 模板；HTML 只渲染 JSON。

`材料形式待确认` 仅在标准描述资格条件、但未说明可接受材料形式时使用。此时只能提示人工确认取证方式，不能凭空要求诊断证明、检查单等特定文件。

## 4. 数据模型

根对象采用 `flash-1.0` 与 `material_precheck` 模式，包含：

`schemaVersion`、`mode`、`meta`、`standardProfile`、`sourceDocuments`、`analysisRecord`、`precheckItems`、`supplementList`、`confirmation`。

`standardProfile` 保存本次采用标准的名称、来源、版本、采用方式、规则解释摘要和结构化标准引用。`sourceDocuments` 分别保留标准来源和每份患者材料的完整原文，禁止合并或摘要。

`precheckItems` 与采用标准的每个提取项一一对应，包含规则标识、提取项标识、条件说明、预检状态、已定位证据、原文定位、信息不足说明和材料形式待确认说明。`supplementList` 只收录状态为信息不足、未定位证据或材料形式待确认的条目。

`confirmation` 同时记录标准采用确认与材料完整性确认；任一未确认均不得生成正式成果。

## 5. HTML 报告

新建专用、离线的单文件模板。页面展示：

1. 本次采用标准与适用边界。
2. 已确认材料清单。
3. 条件—证据预检矩阵。
4. 补充信息/补件清单与优先级。
5. 待人工确认的材料形式。
6. 标准逻辑与原文、患者材料原文、分析记录和确认记录。

页面清楚标注“预检建议，不构成正式资格审核结论”，不得展示审核质控的风险、问题或原审核对照。

## 6. 复用与验收

直接复用审核标准生成 Skill 的规则、提取项、逻辑树、歧义与标准确认原则；参考审核质控 Flash 的材料清单确认和逐规则证据定位；复用材料编目 Flash 的完整原文留存、输入安全与 HTML 数据槽校验。

不复用审核质控 Flash 的原审核结果、两阶段非盲复核、五维质控、风险和问题模型。

验收覆盖：自然语言标准歧义阻断、知识库多候选标准确认、结构化标准直接输入、未确认材料阻断、四种预检状态、标准未规定材料形式、每条补充项可追溯、敏感信息拦截、JSON/HTML 等值。
