# 门诊慢特病认定与审核质控 Flash 模式 1、模式 2 改版设计

## 1. 背景与目标

本次改版来自 Flash skill 在腾讯 ADP 中对脑梗死认定标准和审核质控报告的实际验收。

现有成果可以生成 JSON 和单文件 HTML，但暴露出以下主要问题：

- 模式 1 将提取项平铺展示，规则、提取项和 AND/OR 逻辑之间的层级不直观。
- 模式 1 的规则拆分、原文引用和交付前检查仍容易被模型误解。
- 模式 2 的“同一上下文两阶段复核（非盲）”不够通俗。
- 模式 2 未明确标识哪些事实是本次质控归纳的结果。
- 模式 2 的原始材料位置靠后，原审核结果整段堆叠。
- 模式 2 的实测成果把六份患者材料合并成一条摘要来源，破坏逐份追溯和材料 ID 核验。
- 模式 2 对材料 ID 错引、结论方向与风险方向冲突等问题缺少足够防呆。

改版目标是在不增加外部运行时、不扩展 `flash-1.0` Schema 的前提下，通过契约、检查清单和两个固定 HTML 模板的联合增强，提升 Flash 成果的准确性、可追溯性和业务可读性。

## 2. 设计边界

本次改版保持以下边界：

- 继续支持模式 1“认定标准结构化”和模式 2“审核质控”。
- 保持 `flash-1.0` Schema，不增加、删除或重命名 JSON 字段。
- 不增加 Python、Node、Shell 或其他外部运行时脚本。
- 模型仍只负责形成分析草稿、生成结构化 JSON、将 JSON 写入固定模板数据槽。
- `certification-template.html` 与 `qc-report-template.html` 继续作为两个独立 asset。
- 不增加新的 Flash skill 运行文件，继续保持现有七个文件。
- 标准版 `chronic-disease-certification-qc` 不做修改。
- 原文和可审阅分析记录继续进入 JSON，并在 HTML 中提供展示位置。
- 页面中的状态、风险方向、严重程度和业务提示全部使用中文。
- 两个模板均保留左侧锚点导航。

本次不引入完整版的 Python 校验、哈希绑定、隔离盲审或复杂规则编码体系。

## 3. 总体数据流

统一处理链路保持为：

```text
来源材料
→ 模型形成可审阅分析草稿
→ 模型生成 flash-1.0 JSON
→ 按模式检查清单自检
→ 安全写入对应固定 HTML 模板
→ 校验数据槽和 JSON 往返一致性
→ 交付 JSON + HTML
```

HTML 只渲染 JSON 中已有的业务信息，不生成新的规则、证据、质控判断或建议。

## 4. 通用来源材料约束

`sourceDocuments` 的字段仍为 `name`、`type`、`content`，但补充以下硬约束：

- 一份输入材料必须对应一条 `sourceDocuments`。
- 多份患者材料不得合并成一条摘要或综合描述。
- `content` 必须保存该材料收到时的完整原文，不得用分析结果或摘要替代。
- 有材料 ID 时，`name` 必须包含可识别的材料 ID，完整原文中的 ID 也必须原样保留。
- `confirmation.inventoryShown` 必须与 `sourceDocuments[].name` 的顺序和内容完全一致。
- 用户未明确确认材料清单完整时，不得将 `materialsConfirmedComplete` 或 `confirmation.confirmed` 设为 `true`。
- 材料未确认完整时只返回材料清单和待确认提示，不生成正式 JSON 或 HTML。

上述约束不改变 Schema，但确保模式 2 可以核验原审核引用的材料 ID。

## 5. 模式 1 设计

### 5.1 页面信息架构

模式 1 不再将逻辑、规则和提取项作为彼此割裂的平铺内容。正文改为一棵可逐层展开的层级树：

```text
逻辑关系（AND / OR）
└─ 规则
   └─ 提取项
      └─ 取证与判断指引
```

展示规则如下：

- AND/OR 逻辑主干默认可见，并同时展示中文“且”“或”。
- 每条规则使用原生 `<details>` 节点。
- 规则摘要展示“规则编号 + 规则内容”，不能只展示编号。
- 展开规则后显示该规则的全部提取项。
- 每个提取项继续作为一层 `<details>` 节点。
- 提取项摘要展示“提取项编号 + 名称 + 数据类型”。
- 展开提取项后展示预期证据、反向证据、无法判断条件和优先材料来源。
- 取消现有独立的平铺提取项卡片。
- “逻辑关系”“规则”“提取项”仍各自拥有可定位的锚点，但属于同一棵正文层级树。
- 键盘可以聚焦并操作展开节点，焦点状态清晰。
- 打印样式强制展开全部层级，避免导出时遗漏折叠内容。

逻辑区顶部增加“本次标准整理初步结论”，内容来自 `analysisRecord.preliminaryConclusion`，并明确它是本次分析结果，不是政策原文。

### 5.2 规则拆分语义

模式 1 契约增加明确规则：

- 规则之间的 AND/OR 关系必须由 `logic` 表达。
- 同一条规则内部的多个条件如果全部必须满足，可以保留在一条 `content` 中。
- 同一条规则内部出现“任一满足即可”的 OR 分支时，必须拆成多条规则，再由 `logic` 的 OR 组组合。
- 如果 AND/OR 歧义会改变规则拆分或最终逻辑，它属于阻断性歧义。

该设计不增加 `subconditions` 等新字段。

### 5.3 来源原文与基础信息

- `sourceQuote` 必须是某一来源 `content` 中的连续原句。
- 不得拼接不连续片段，不得改写文字或标点。
- 模板发现 `sourceQuote` 无法精确定位时显示非阻断中文警告，但仍允许报告打开。
- `diseaseCode` 允许为空；HTML 统一显示“未提供编码”，不得把空编码视为标准无效。
- `VYYYYMMDD` 形式的交付版本明确解释为成果生成日期，不得表述为政策发布日期。

### 5.4 歧义处理与交付检查

- 阻断性歧义包括会改变规则条件、规则拆分、AND/OR、阈值、单位、范围或排除条件的问题。
- 非阻断性问题包括不改变规则含义的措辞、排版和展示偏好。
- 模型必须一次性列出当前已发现的全部阻断性歧义，避免逐个往返询问。
- 阻断性歧义未解决时不得生成正式 JSON 或 HTML。

模式 1 检查清单拆成可逐项执行的十项检查，至少覆盖：

1. JSON 可解析且无注释、尾逗号。
2. 根字段集合与契约完全一致。
3. 来源材料逐份、完整保存。
4. 每条 `sourceQuote` 是来源中的连续原句。
5. 规则 ID 连续且唯一。
6. 提取项 ID 全局连续且唯一。
7. 每条规则在逻辑树中恰好出现一次，引用集合完全相等。
8. 顶层及嵌套 AND/OR 与用户确认一致，提取项七个字段完整且类型合法。
9. 用户确认记录真实、完整且非空。
10. HTML 数据槽可解析并与交付 JSON 逐字段等值。

## 6. 模式 2 设计

### 6.1 页面章节顺序

模式 2 的正文及左侧导航统一调整为：

1. 结论总览
2. 输入范围
3. 原始材料
4. 五维检查
5. 问题清单
6. 逐规则复核
7. 建议
8. 分析记录
9. 确认记录

### 6.2 两阶段非盲复核说明

底层 `baseReview.method` 继续使用 `two_stage_non_blind`，页面展示名称改为：

> 两阶段复核：先独立判断，再对照原审核

页面辅助说明为：

> 第一阶段仅依据患者材料和认定标准形成独立结论；第二阶段再检查原审核的证据、推理和结论。原审核结果在同一任务中可见，因此属于非盲复核。

契约补充强约束：

- 形成 `baseReview.materialFacts`、`ruleJudgments` 和 `preliminaryResult` 时，不得引用 `audit_result` 中的结论、证据或推理。
- `baseReview` 完成后才能读取原审核内容并形成 `auditComparison`。

这是流程隔离，不宣称具备严格盲审能力。

### 6.3 结论总览

结论总览并排展示：

- 本次独立复核结果。
- 原审核结论。
- 两者方向一致、相反或无法判断。
- 质控结论。
- 风险方向。

风险、状态和结论均翻译为中文。用户无需在“独立复核”和“审计对比”之间来回查找。

### 6.4 原始材料与原审核结构化展示

“原始材料”移动到第 3 节。每份患者材料、认定标准和原审核结果都使用独立的可展开节点。

原审核结果采用“结构化摘要 + 可展开完整原文”：

1. 原审核内容是有效 JSON 时，模板按对象和数组层级递归展示。
2. 原审核内容是普通文本时，模板只识别能够明确定位的最终结论、逐规则结果、提取项、证据引用和审核建议。
3. 无法可靠识别的普通文本按自然段展示，不臆造结构。
4. 结构化解析失败只影响摘要展示，页面降级到自然段和完整原文。
5. “查看完整原文”始终展示未经改写的 `sourceDocuments[].content`。

患者材料、认定标准和原审核结果类型统一显示为中文。

### 6.5 本次质控事实与逐规则复核

`baseReview.materialFacts` 的展示名称改为“本次质控提取的患者材料事实”，并增加说明：

> 以下内容由本次质控根据患者材料归纳形成，用于独立复核，不代表原审核结论；原始依据以“原始材料”中的完整原文为准。

该内容只在“逐规则复核”顶部展示，不在“输入范围”中重复。

规则编号约束：

- `standardKind=structured` 时，`ruleJudgments.ruleId` 必须直接复用结构化标准中的规则码。
- `ruleJudgments` 的规则集合必须覆盖标准逻辑树引用的全部规则。
- `standardKind=natural_language` 时继续使用 `TMP-R001` 起的临时编号。
- 模板对 `TMP-` 规则显示“本次质控临时规则，非正式业务标准”。

### 6.6 材料 ID 与问题判定

- 原审核引用的任何材料 ID 必须能在 `patient_material` 类型来源的名称或完整原文中定位。
- 无法定位的引用必须形成“证据提取准确性”问题，严重程度至少为“中”。
- 证据真实成立不能掩盖材料 ID 错引。
- 模板在问题清单中高亮材料 ID。
- 能定位的 ID 提供到对应原始材料的页内跳转。
- 无法定位的 ID 显示“引用材料未在本报告材料清单中”的非阻断警告。

### 6.7 质控结论与风险方向

- 当且仅当五个维度全部为“通过”且 `issues` 为空时，才能使用 `reliable`。
- 只要存在任何问题，包括材料 ID 错位或证据错引，即使结论方向一致，也必须使用 `problematic`。
- `problematic + risk=none` 表示存在局部问题，但不改变通过或不通过方向。
- 原审核通过、本次独立复核不满足，对应错误通过风险。
- 原审核不通过、本次独立复核满足，对应错误拒绝风险。
- 方向信息不足时使用不确定结论和未知风险。

模板增加方向一致性校验。中文结论归一化时必须先识别“不通过”“拒绝”“不予通过”等否定表达，再识别“通过”，避免包含关系误判。风险方向与两侧结论冲突时，模板显示中文数据错误并阻止错误报告正文渲染。

### 6.8 受限检查

- `not_checked` 卡片突出显示“本项因输入受限未核查”。
- `notCheckedReason` 使用更高视觉权重，不能与普通摘要混在一起。
- 用户没有明确确认材料完整时不得默认确认，也不生成受限的正式成果。
- `conclusion_only`、`brief` 和标准缺失的既有降级逻辑继续保留。

## 7. 模板校验和安全降级

正式成果阻断条件包括：

- JSON 无法解析或根字段不符合契约。
- 数据槽占位符缺失、重复或写入后无法还原为等值 JSON。
- 用户未确认材料清单完整。
- 来源原文缺失，或多份材料被合并为摘要。
- ID 重复、逻辑树漏引或重复引用规则。
- 状态、严重程度或风险使用非法值。
- 模式 2 独立复核方向、原审核方向和风险类型冲突。
- 模式 2 五个维度缺失、重复或顺序错误。

以下情况不阻断页面打开：

- 模式 1 `sourceQuote` 无法在来源中精确定位。
- 模式 2 原审核普通文本无法自动结构化。
- 模式 2 原审核引用材料 ID 无法在患者材料中定位。
- 输入受限导致某一维度无法核查。

这些情况必须显示中文弱提示或明确的“未核查”状态。

JSON 写入模板前继续将字面字符 `<`、`>`、`&` 转义为 `\u003c`、`\u003e`、`\u0026`。写入后重新提取数据槽，执行 `JSON.parse`，并与交付 JSON 逐字段比对。

## 8. 测试与验收

实施采用测试先行，覆盖以下行为：

### 8.1 模式 1

- 逻辑组、规则、提取项形成三层嵌套 DOM。
- 页面不再生成独立平铺的提取项卡片。
- 规则摘要展示规则内容，提取项摘要展示名称和类型。
- 原生展开、收起、键盘焦点和左侧锚点可用。
- 打印样式展开全部层级。
- 初步结论在逻辑区顶部展示。
- 空疾病编码显示“未提供编码”。
- `sourceQuote` 定位失败显示非阻断警告。
- 规则拆分、连续 ID、逻辑覆盖和十项检查通过契约文本测试与变异测试。

### 8.2 模式 2

- 页面和左侧导航使用新的九节顺序。
- 复核方法使用通俗中文说明。
- 独立复核、原审核和方向判断并排展示。
- 每份来源材料分别展示，不接受合并来源。
- 原审核有效 JSON、可识别普通文本和不可识别文本分别覆盖结构化、分段及降级路径。
- 完整原文始终可展开且与 JSON 内容一致。
- “本次质控提取的患者材料事实”标签和说明正确。
- 结构化标准规则码直接复用，临时规则显示提示。
- 材料 ID 可定位时可跳转，不可定位时显示警告。
- 存在局部问题但方向一致时使用“存在问题 + 无方向性风险”。
- 风险方向冲突时模板阻断错误正文。
- `not_checked` 原因醒目显示。

### 8.3 通用回归

- 两个模板的数据槽安全写入和 JSON 往返一致。
- 页面不直接显示英文状态、风险或严重程度。
- Flash skill 全量测试通过。
- 标准版 skill 的既有测试保持通过。
- 使用实际模式 1、模式 2 验收 JSON 生成 HTML 并进行浏览器检查。

## 9. 完成标准

满足以下条件时本次改版完成：

- 模式 1 的规则和提取项具有与标准版一致的逐层展开逻辑。
- 模式 2 能明确区分本次质控结果、原审核结果和完整原始材料。
- 原始材料逐份保存，材料 ID 可追溯。
- 原审核结果具有结构化摘要，同时完整原文不丢失。
- 关键契约错误能够阻断，展示性或解析性问题能够安全降级。
- 未增加 Schema 字段、外部运行时脚本或 Flash skill 运行文件。
- Flash 与标准版回归测试均通过。
