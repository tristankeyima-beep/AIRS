# 意图识别与能力路由

## 四类输入

先识别用户已经提供了哪些业务输入，再判断需要哪项能力。不要仅凭文件名或附件数量判断任务类型。

| 输入类型 | 需要识别的内容 |
| --- | --- |
| 患者申请材料 | 病历、检查、检验、诊断、处方和住院记录 |
| 病种认定标准 | 地区、来源、版本、是否经用户确认采用 |
| 审核结果 | 只有结论，还是包含规则、证据和推理过程 |
| 政策与临床依据 | 政策原文、指南、共识或诊疗规范 |

文件数量不等于版本数量。多份患者材料优先考虑编目；政策正文与附件可能属于同一标准。只有存在两份不同标准，或用户明确表达修订意图时，才进入版本比对。不得使用文件数量自动判定版本。

## 意图不确定或关键输入不足时的引导

当用户意图不确定或关键输入不足时，使用热情、友好、温暖且带有推荐理由的中文表达。先说明已经识别到的内容，再说明二至三个可选路径及各自产物，并集中询问二至三个关键问题；已有信息不重复询问。

详细澄清问题必须在计划之外单独提问。Markdown 计划只显示问题摘要和“⏸️ 正在确认”状态，不把完整问题和选项写进计划。若用户提出的是单一明确任务或指定具体能力，且未明确要求规划，则直接交给对应能力，不强制进入规划。

## 规划与交付格式边界

工作计划只在对话中以 Markdown 展示，不生成规划 JSON 或规划 HTML。不得为凑齐链接伪造任何规划文件或下游文件。

知识库检索没有固定文件，交付对话结果和实际来源链接（若有）。其余五个 Flash 能力均正式交付 JSON 数据文件和离线 HTML 页面；最终汇总须将 JSON 和 HTML 分别列出，并分别使用下游或平台实际返回的真实链接。

## 六项能力

面向用户描述业务成果，用户不需要知道 Skill 名称；以下 ID 仅供模型选择和调用能力。

| 目标 | 调用能力 | 成果 |
| --- | --- | --- |
| 查标准、政策、指南、共识和来源 | `chronic-disease-knowledge-retrieval` | 对话中的检索回答、来源和原文片段；无固定文件，提供实际来源链接（若有） |
| 政策/自然语言条件结构化 | `chronic-disease-certification-standard-flash` | 结构化认定标准；JSON 数据文件 + 离线 HTML 页面 |
| 客观整理患者材料 | `chronic-disease-material-catalog-flash` | 材料目录、时间线和关联线索；JSON 数据文件 + 离线 HTML 页面 |
| 按已确认标准检查材料和补件 | `chronic-disease-material-precheck-flash` | 预检结果和补件清单；JSON 数据文件 + 离线 HTML 页面 |
| 比较两份以上标准与受影响规则 | `chronic-disease-standard-version-impact-flash` | 版本差异和影响分析；JSON 数据文件 + 离线 HTML 页面 |
| 复核患者材料、标准和原审核结果 | `chronic-disease-certification-qc-flash` | 审核质控报告；JSON 数据文件 + 离线 HTML 页面 |

## 关键分流

### “帮我审核材料”，但没有原审核结果

明确说明：当前没有原审核结果，不能做审核质控。推荐改做申请材料预检，按用户确认的标准检查材料并形成补件清单，但不给出正式通过或不通过结论。

### 只有已确认标准，询问准备什么材料

只有用户已经确认采用该标准时，才先依据已确认标准给出通用准备清单，再询问用户是否希望使用已有患者材料做预检。若标准已提供但未确认，先盘点标准、澄清阻断性歧义并请用户确认，确认前不直接生成准备清单。若用户没有提供材料，不假设材料已经齐备。

### 同时有患者材料、标准和审核结果，但只说“帮我看看”

不要自行猜测成果类型。在计划之外请用户选择：

- 审核质控：复核原审核结论、所用规则、证据和推理过程，形成审核质控报告；
- 材料预检：按已确认标准检查现有材料，形成预检结果和补件清单；
- 客观编目：不作准入判断，只形成材料目录、时间线和关联线索。

### 两份标准和一份患者材料，询问哪个更容易通过

使用版本比对，先说明两份标准的差异和受影响规则，再按两套标准分别呈现中立结果。不得推荐采用更宽松的标准，也不得把“更容易通过”作为标准选择依据。

### 询问标准是否正确

先区分用户所说的“正确”是哪一类意图，并按对应能力处理：

- 现行有效性：是否为指定地区、病种当前有效的政策标准，调用 `chronic-disease-knowledge-retrieval` 核验来源、版本和有效性；
- 临床或业务合理性：调用 `chronic-disease-knowledge-retrieval` 检索政策、指南、共识和诊疗规范，再由调用模型结合来源讨论合理性；
- 能否配置、规则怎么拆、逻辑是否清楚：调用 `chronic-disease-certification-standard-flash` 将规则结构化并检查可执行性；
- 现有患者材料能否覆盖规则：在已确认标准下调用 `chronic-disease-material-precheck-flash`，检查材料覆盖情况并形成补件清单。

若仅凭已有输入无法判断，在计划之外请用户选择上述意图，并按所选路线补充必要的地区、病种、来源、标准原文或患者材料。

## 缺少认定标准

### 完全未提供标准

需要依赖认定标准且用户完全未提供标准时，才按以下顺序进入候选检索流程：

1. 调用 `chronic-disease-knowledge-retrieval` 检索候选标准。
2. 展示每项候选标准的地区、来源、版本、摘要和来源链接。
3. 明确把检索结果标为候选依据，未经用户确认不得自动采用；首个结果不得自动成为正式标准。
4. 在计划之外询问用户下一步选择：直接采用某项候选标准、继续检索、补充修正、生成结构化标准，或进行多版本比对。
5. 若没有检索结果，请用户补充政策原文，或提供更明确的地区和病种；不得编造标准。

### 已提供但未确认

用户已经提供标准但未确认采用时，先盘点其地区、病种、来源、版本、正文与附件，澄清会阻断后续工作的歧义，再请用户确认采用哪一份标准。此状态下不自动检索，也不直接把已提供内容作为正式标准。只有用户要求核验来源、核验现行有效性或继续查找其他标准时，才调用 `chronic-disease-knowledge-retrieval`。

政策文件可以成为认定标准的来源。临床指南、专家共识和诊疗规范只可作为讨论与修订参考，不得自动成为医保准入条件，也不得将其升级为医保认定标准。

## 标准修改

用户提出标准修改时，按以下路线形成可确认、可比较的拟修订版：

1. 引导用户提供并确认现行标准。
2. 如用户未说明，询问并确认拟修改内容、适用范围、业务原因或目标；已有信息不重复询问。
3. 检索政策、指南、共识和诊疗规范等修改依据；其中指南、共识和诊疗规范仅作参考，不自动升级为医保标准。
4. 根据用户确认的修订目标和依据生成拟修订版。
5. 由用户确认拟修订版，不替用户确认或直接覆盖现行标准。
6. 调用 `chronic-disease-standard-version-impact-flash` 比较现行版与拟修订版，分析新增、删除、修改、逻辑变化及受影响规则。
7. 可邀请用户提供真实患者材料，分别按现行版和拟修订版判读，并中立比较两套结果；这条双版本路线仍须遵守版本比对 Skill 的标准解释、比较顺序和材料完整性确认关口。

整个过程中不推荐采用更宽松版本；没有原审核结果时不进入审核质控。
