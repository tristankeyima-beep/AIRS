# 结构化认定标准生成规范

## 来源边界

只使用用户提供的认定信息。病种名称仅用于理解上下文，不得自动补充确诊、检查、治疗、机构等级、并发症、排除条件、阈值等外部医学或政策知识。

## 规则拆解

只有直接决定认定资格的准入条件生成规则；辅助细则只能补强对应规则的证据口径，不得独立升级成规则。一个复合准入条件可以是一条规则，但其提取项必须原子化：一个提取项只验证一个原子事实。

## 提取项

每个提取项必须说明肯定证据、反向证据、无法判断边界和优先材料位置。enum 的语义必须覆盖满足、不满足和无法判断；string 的 enumOptions 固定为 []。

## 逻辑

保留 AND/OR 与共同前提条件的嵌套层级，不得扁平化。共享前提条件应保留在其适用的分支外层，不能复制后改变其约束范围。

## 编码

草案临时规则使用 R001、R002 等连续标识。正式编码只能由脚本生成；模型不得选择或填写正式规则编码、提取项编码。

## 版本

版本优先级为用户版本 > 来源版本 > 生成日期 VYYYYMMDD。若用户和来源都没有版本而使用该回退值，必须在 meta.description 和交付摘要中明确记录“生成日期，不是政策发布日期”。

## 正式文件名

JSON 使用 `<病种>-certification_list-<版本>.json`；HTML 使用 `<病种>-认定标准可视化-<版本>.html`。

## 阻断性歧义

AND/OR、阈值、单位、时长、次数、范围、排除条件、共同前提条件、来源冲突或病种编码冲突无法唯一确定时，必须逐项向用户提出有针对性的问题，不得猜测，也不得用含糊表述掩盖歧义。

若用户说不知道、无法决定，或仍有任何阻断性歧义未解决，停止在明确标记的“待确认提案”，不得生成正式 JSON 或 HTML。用户明确同意不能代替阻断性歧义的解决；只有全部歧义解决后，才能重新展示拟采用的规则、提取项和逻辑，并取得用户明确同意后再继续。修订后重复该确认关口。

## 常见错误

- 把来源之外的诊断、检查、治疗、机构、并发症、排除条件或阈值写入认定标准。
- 把辅助证据细则升级为独立资格规则，或把一个提取项写成多个原子事实。
- 展平 AND/OR 或共同前提条件，改变原始适用范围。
- 在用户明确同意前生成正式 JSON 或 HTML，或让模型分配正式编码。
- 将用户“同意”误作未决阈值、逻辑或范围的解决，或在待确认提案阶段生成正式文件。
